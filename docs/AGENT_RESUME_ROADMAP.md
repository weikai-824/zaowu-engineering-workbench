# Agent 应用版路线图（三个交付目标）

## 项目目标

把现有“造物工程台”的圈选改版能力升级为一条真实、可恢复、可验证的工程返工闭环：

`圈选区域 + 文字要求 → Agent 规划 → 人工确认 → 工具真实返工 → 工程校验 → 必要时重规划 → 新版本重新呈现`

这条能力首先服务 **Python Agent 应用开发** 的工程深度，同时自然覆盖比赛中的真实返工需求。Agent 不是额外增加的聊天入口，而是负责跨模型理解、工程工具、长任务、版本和验证结果的可靠编排层；不能为了比赛演示压缩状态图或可靠性设计。

## 已锁定的技术边界

- Agent 服务：Python 3.12、FastAPI、LangGraph。
- 主范式：Planner–Executor–Verifier–Replanner。
- ReAct：只允许在 Planner/Replanner 内做有界推理，配置最大步数与预算。
- Agent 状态：PostgreSQL + 官方 LangGraph checkpointer。
- 业务数据：继续使用 D1/R2，不为 Agent 迁移。
- 产品端：保留现有 TypeScript/Vinext 应用，作为 UI、业务系统和受控 Tool Gateway。
- Agent 只能经 Tool Gateway 读取项目、提交任务、附加结果和创建版本，不能直连 D1/R2、Tripo 或本机执行器。
- 编排边界：一个业务状态图；不建设多 Agent swarm、A2A 或“比赛 Agent”。
- 交付终点：下述目标 3。公开部署与长期生产运维继续暂缓。

当前产品已经能够：

- 在三维视图中圈选区域，记录零件、对象、三角面、世界/局部坐标、相机视角和归一化圈选路径；
- 保存带圈截图，并把圈选上下文与用户文字一起提交给多模态模型；
- 生成经过 schema、白名单和工程证据约束的结构化建议；
- 人工点击应用部分参数修改，并创建新的 Project Revision；
- 创建 CAD Job、交给受控本机执行器、校验签名结果、附加新资产并保存新版本。
- 由 Python Agent 通过 Tool Gateway 编排整条返工链；缺少工程事实时先澄清再重规划，计划批准前不执行副作用。
- 将执行状态、证据、模型 token/成本、工具次数和重规划次数持久化到 LangGraph checkpoint，并在页面恢复 Run 时间线。

联合服务链已经在本机 Docker/PostgreSQL、真实模型和已配对 CAD 执行器同时在线时跑通：早期测试副本从 revision 1 推进到 revision 3，`outer_width` 从 130 变为 132，四个锁定 M3 接口保持不变，四个新 CAD 资产带受控来源附加，最终 Run 为 `succeeded`；服务重启后 checkpoint 可恢复。2026-09-27 又从真实浏览器画圈完成 136 → 138 mm 的独立副本验收，并修复长返工面板遮蔽模型的问题。受控 CAD 首条链路的浏览器回显已验证；任意外观网格精修、实物验证和人工现场录屏仍不能据此宣称完成。

## 目标 1：打通一条真实返工闭环

### 用户结果

用户对一个可参数化 CAD 零件画圈并输入修改要求，审核 Agent 计划后，系统真实修改参数、运行 CAD、产出并附加新的模型资产、执行数字检查，最后在原工作台展示新版本和修改前后差异。

### 建设范围

1. **返工任务契约**
   - 定义 `RepairRequest`、结构化 `RepairPlan`、Tool Result、Verification Result 和终态结果。
   - 请求绑定 `projectId`、`baseRevision`、圈选反馈、目标零件、用户要求和 `clientRequestId`。
   - 每个计划步骤声明前置条件、预计副作用、审批要求、预算和完成证据。

2. **受控 Tool Gateway**
   - 先开放完成黄金链路所需的最小工具：读取项目快照、保存受控 CAD 参数、创建 CAD Job、提交执行、查询结果、附加 CAD 资产、执行数字检查、读取新 Revision。
   - 固定 Python/TypeScript JSON Schema、鉴权传递、幂等键、超时、结果大小和错误分类。
   - 任何白名单外调用都必须被拒绝；重复执行不能产生第二个 CAD Job 或重复 Revision。

3. **LangGraph 业务状态图**
   - 实现 Planner、Clarification、Approval、Executor、Verifier、Replanner 与明确终止节点。
   - 计划和重规划使用结构化输出；设置循环、token、工具次数、时间和成本预算。
   - 每一步进入 PostgreSQL checkpoint；进程重启后从原 `thread_id` 继续。

4. **人工确认与真实执行**
   - Planner 缺少尺寸或约束时进入 clarification interrupt；回答必须先经过 Replanner，新计划仍需审批。
   - 修改工程版本、启动本机 CAD 等副作用发生前进入 approval interrupt。
   - 用户可批准、拒绝或补充约束；批准后才执行。
   - Verifier 必须检查新资产来源、CAD hash、目标 Revision、几何检查结果以及圈选目标是否仍然有效。

5. **最小闭环 UI**
   - 将当前“应用可执行修改”接入 Agent Run，而不是直接结束在 `/api/ai/apply`。
   - 展示计划、待审批、执行中、等待本机、验证中、重规划、成功或失败。
   - 成功后自动载入新 Revision 和新几何，并提供返工前/后的明确入口。

### 首条支持边界

- 首条闭环只承诺 **受控参数化 CAD 返工**，因为它有真实可执行工具和可验证产物。
- 圈选用于定位修改意图，不等于从二维轮廓精确反求三维几何。
- 任意 STL/OBJ/GLB 的局部雕刻不在首条闭环内；无工具支持时必须返回 `needs_engineering_review`，不能声称已完成。
- Tripo 重新生成的候选只能标为新视觉候选，不能冒充对原制造模型的确定性局部修改。

### 完成证据

- 一个固定 Golden Scenario 从圈选开始，最终产生新的 CAD Asset 和 Project Revision，并由工作台重新加载显示。
- 成功、工具失败、校验失败后重规划、用户拒绝、预算耗尽五条图路径都有自动化测试。
- 在等待 CAD 时重启 Agent 服务，任务能恢复且不重复提交。
- 审批前 D1/R2、CAD Job 和 Project Revision 均无副作用。
- Python 单元/集成测试、跨语言契约测试和现有根质量门禁全部通过。

### 比赛冻结副本处理门

目标 1 验收后，先核对冻结版中的源码、本地 D1/R2 状态和演示证据是否已在当前工程或独立归档中可恢复；得到用户明确确认后，才能删除冻结副本。规划本身不授权删除。

## 目标 2：把单条闭环做成可靠的返工 Agent 产品

### 用户结果

返工不再依赖一次理想演示：页面关闭、服务重启、执行器暂时离线、重复回调、版本冲突或校验失败时，用户仍能看到真实状态，恢复原任务，或依据 Agent 的重规划继续处理。

### 建设范围

1. **扩充受控返工能力**
   - 支持修改现有 CAD 参数、创建白名单 CAD 设计、底座尺寸调整和重新附加派生资产。
   - 对视觉生成任务可创建“新候选版本”，但必须与制造 CAD 返工分轨显示。
   - 建立能力矩阵：`executable`、`generative_candidate`、`human_required`，由工具能力而不是模型话术决定可执行性。

2. **可靠性与恢复**
   - 完成批准、拒绝、修改要求后继续、取消、超时、重试和页面关闭后恢复。
   - 区分可重试、不可重试、状态未知、需补充输入、需人工处理错误。
   - 对 CAD/Tripo 等有成本工具实施幂等、退避、轮询/回调去重和重试预算。

3. **验证与重规划**
   - 将 schema、来源、版本冲突、几何/拓扑、锁定接口和所需工程检查转成结构化 Verification Result。
   - 校验失败时，Replanner 只能在剩余预算和允许动作内修改计划；不能删除约束或绕过审批。
   - 明确区分“已执行”“数字检查通过”“需要人工工程复核”“物理验证未执行”。

4. **任务时间线和版本对比**
   - 页面展示步骤时间线、工具输入摘要、证据、等待对象、失败原因、重规划原因、预算和人工决定。
   - 提供返工前后版本切换、几何对比和审计轨迹；刷新页面后仍可查询。
   - 旧的建议面板降级为 Run 的计划/审批视图，不再形成第二套孤立流程。

### 完成证据

- 至少三类固定任务：参数修改成功、创建新 CAD 设计、不可自动执行的导入网格局部返工。
- 断网、进程重启、执行器离线、重复回调、Revision 冲突、工具超时、验证失败均有失败注入测试。
- 所有副作用工具满足幂等测试；同一 `clientRequestId` 不产生重复费用或重复版本。
- 用户仅凭时间线能够判断任务停在哪里、为什么停、下一步由谁处理。
- 至少一条校验失败场景能够在约束和预算内重规划后成功；无法修复时诚实终止。

## 目标 3：完成 Agent 工程质量闭环

### 用户结果

Agent 工作流具备可重复评测、端到端可观测性与安全护栏；每项可靠性结论都有测试、日志或运行证据，不依赖一次理想演示。

### 建设范围

1. **评测体系**
   - 建立版本化任务集，覆盖成功、澄清、拒绝、工具失败、验证失败、重规划、恢复和人工升级。
   - 自动统计任务成功率、计划有效率、平均步骤数、工具错误恢复率、checkpoint 恢复率、重复副作用次数、成本和延迟。
   - 固定模型、提示词版本、工具版本和测试输入，使结果可复现。

2. **可观测性与安全护栏**
   - 打通 request/run/thread/tool/revision/evidence 关联，输出结构化日志、trace 和核心指标。
   - 测试 prompt injection、越权工具、参数污染、项目越权、预算穿透、审批绕过和敏感字段泄露。
   - 关键安全和恢复用例进入 CI；运行日志和展示数据完成脱敏。

3. **架构与回归证据**
   - 维护架构图、返工时序图、LangGraph 状态图、Tool Gateway 契约、技术决策和能力边界文档，服务于实现和维护而不是包装材料。
   - 固定三条端到端回归：正常闭环、验证失败后重规划、服务重启后恢复。
   - 做全量回归并核对 README 与 UI 文案，不把视觉候选、数字检查或软件执行夸大为制造验证。

### 完成证据

- 固定评测命令可生成机器可读结果和人类可读报告，关键指标能追溯到单个 Run。
- 三条端到端回归在干净环境按文档可重复运行，不依赖人工修改数据库或伪造成功状态。
- 安全、恢复、跨语言契约、前后端回归和生产构建全部通过。
- 状态图、工具编排、持久化、审批、恢复、评测与安全均有代码和自动化证据。
- 仓库文档和产品 UI 对已完成能力及未完成边界保持一致。

## 推进与汇报方式

- 后续以“目标”为单位连续推进，不再为每个小模块暂停等待。
- 每个目标内部仍保留可回滚的小提交和自动化质量门禁。
- 只有达到该目标的全部完成证据后才汇报验收并进入下一目标。
- 若发现首条黄金链路无法由现有真实工具完成，应先修正工具或缩小被明确声明的能力边界，不能用模拟结果替代。
